# Parrot LMS

A production-grade Learning Management System. Next.js (App Router) delivers everything: user identity (email/password, bcrypt), the course platform (browsing, lessons, progress tracking, analytics), and admin course/content management. MongoDB (via Prisma) is the single source of truth for all of it.

Paid courses add one optional piece: **GoHighLevel as the checkout/payment processor**. A course's "Buy" button links out to a GoHighLevel checkout page; after a *successful* payment, a GoHighLevel workflow calls this app's webhook, which — idempotently, keyed on the GHL transaction id — creates the buyer's account from their checkout email (no password yet), enrolls them with **lifetime access**, records the payment. **The checkout redirects the buyer straight to `/welcome`, where they choose their own username and password** and are signed in. **A purchase causes no email at all**: the app sends none itself and writes nothing to the buyer's GoHighLevel contact (no field, no tag), so it cannot set off a GoHighLevel workflow either — the only emails buyers get are the ones you build in GoHighLevel yourself. The single exception is *Forgot password*, which the account's owner requests (see step 7 below). The course is only accessible after signing in with exactly those credentials (stored bcrypt-hashed); any other password is rejected, and every course/lesson read re-checks the enrollment server-side. A refund/chargeback workflow calls a second webhook that revokes the access (the account survives). Free courses skip this entirely (one-click self-enroll). GoHighLevel is *not* required for the app to run — only for selling paid courses.

```
Next.js (identity, course platform, learning experience, admin CMS)
        │
        ▼
MongoDB (users, course content, progress, analytics, enrollments, payments, email log)

Next.js  ──courses/[slug] "Buy" button──▶  GoHighLevel checkout
   ▲                                              │ payment SUCCESS
   │◀── purchase workflow webhook (shared secret)─┘
   │ verify secret + payment status
   │ idempotency check (transaction id)
   │ create user (no password yet)
   │ enroll (lifetime, status ACTIVE) + record Payment
   │ (nothing is sent back to GoHighLevel: no email)
   │
   │◀── checkout redirects the buyer's browser to /welcome
        buyer types the checkout email, chooses a username +
        password (bcrypt), is signed in; later logs in at
        /login. The server re-checks the enrollment on every
        course read
```

A parallel Stripe Checkout integration also exists (`src/features/payments/`) but isn't wired to any button currently — GoHighLevel is the live path.

## Stack

Next.js 16 (App Router, Turbopack) · React 19 · TypeScript (strict) · Tailwind CSS v4 · shadcn/ui (Base UI) · Prisma 6 on MongoDB · Auth.js v5 · Zod · Zustand · Recharts · Tiptap · Vitest · Playwright.

**Note on Prisma:** pinned to 6.19.3, not 7.x — Prisma 7 dropped MongoDB support ("coming soon" per their own docs as of this writing). Don't upgrade the `prisma`/`@prisma/client` packages without checking that's changed.

## Architecture

A modular monolith. Business logic lives under `src/features/<domain>/{schemas,services,repositories,types,actions}`; UI lives under `src/app` (routes) and `src/components` (presentational only — no business logic in components). See `AGENTS.md` (auto-generated by Next.js) for framework-level notes, and the domain folders themselves for the real map: `auth`, `users`, `courses`, `modules`, `lessons`, `enrollments`, `progress`, `analytics`, `access` (course access checks + the GoHighLevel purchase webhook), `quizzes`, `media`, `notifications`, `search`.

Authorization is always enforced server-side (`src/lib/permissions`, each service's own checks) — never trust a client-supplied role, ownership, or "has access" claim.

## Local setup

### 1. MongoDB

Needs to run as a **replica set** (even single-node) — Prisma uses multi-document transactions for progress recalculation, which plain standalone MongoDB doesn't support.

- **Docker** (see `docker-compose.yml`): `docker compose up -d`
- **No Docker**: download a portable MongoDB build (e.g. from mongodb.com) and run:
  ```bash
  mongod --replSet rs0 --port 27017 --dbpath <some-dir> --bind_ip 127.0.0.1 &
  mongosh --eval "rs.initiate({_id:'rs0',members:[{_id:0,host:'127.0.0.1:27017'}]})" mongodb://127.0.0.1:27017
  ```
- **MongoDB Atlas** free tier: already a replica set, no extra config.

### 4. GoHighLevel (optional -- only needed for paid-course checkout)

Free courses (price $0) work with no GoHighLevel at all. To sell a paid course:

1. **Secret** -- set `GHL_WEBHOOK_SECRET` to a random string (`openssl rand -hex 32`).
2. **API token** -- *Settings -> Private Integrations*, create one with the `View Contacts` and `Edit Contacts` scopes. Put it in `GHL_API_TOKEN`. (Only *Forgot password*, step 7, uses it; purchases never call the GoHighLevel API.)
3. **Custom field** -- *Settings -> Custom Fields*, add one contact field (single line text) with the unique key `contact.course_login_url` (or set `GHL_LOGIN_URL_FIELD_KEY` to match yours). It receives the link a user asked for on *Forgot password* (step 7) -- nothing else is ever written to a contact.
4. **Checkout** -- create the product and its funnel order form / payment link in GoHighLevel, then paste that page's URL into the course's "GoHighLevel checkout URL" in the admin panel (`/admin/courses/{id}`). The same checkout URL can be pasted on every paid course: one purchase opens them all.
5. **Purchase workflow** -- create one workflow (this is what grants access — no webhook, no account):
   - Trigger: *Payment Received* (or *Order Submitted*), filtered to your product, **successful payments only**.
   - Action *Webhook*: `POST https://<your-domain>/api/webhooks/gohighlevel/purchase`, with Custom Data:
     - no course needs naming: **every purchase unlocks every published course**. The buyer is enrolled in everything published at purchase time, any course published later opens the first time they visit it, and inside the platform they see no prices and no Buy button. (A `course_slug` field is still accepted from older workflows and ignored.)
     - `secret` = `GHL_WEBHOOK_SECRET` (or send it as an `x-webhook-secret` header instead)
     - `transaction_id` = the payment/order id merge tag (e.g. `{{payment.id}}` / `{{order.id}}`) — **recommended**: it's the idempotency key that makes a redelivered webhook a safe no-op (no duplicate account or access)
     - optionally `payment_status` = `{{payment.status}}` (anything non-successful is rejected), `amount`, `currency`, `product_id` (bookkeeping on the Payment record)
6. **Redirect after checkout** -- on the order form / payment link, set the page shown after a successful payment to `https://<your-domain>/welcome` (a funnel thank-you step can redirect there instead). The buyer lands on it straight from checkout, types the email they paid with, **chooses their own username and password**, and is signed in -- no email involved. The email is verified against the recorded purchases as it is typed, so a wrong one is refused before a password is chosen. A new member then lands on `/offer`, a standalone one-time offer page (its own HTML and stylesheet in `src/app/offer`, no platform menu) whose "No thanks" leads on to the dashboard. A checkout whose buyers should skip the offer redirects to `https://<your-domain>/welcome?next=course` instead: they open the dashboard right after creating their login. Later, the first time a buyer signs in through the login form (`User.firstLoginAt` records it; the automatic sign-in on `/welcome` does not count), they land once on `/thank-you` -- another standalone page (`src/app/thank-you`) whose "Access Course" button leads to the dashboard. Every later login goes straight to the dashboard. If your checkout can merge contact fields into the URL, `?email=<buyer email>` pre-fills the email field. The redirect carries no proof of payment, so the page only sets up an account the purchase webhook (step 5) created, that has no password yet, within 24 hours of the payment; it waits up to a minute for the webhook when the redirect arrives first. After 24 hours the buyer uses *Forgot password* (step 7). **The purchase itself sends nothing**: the app adds no tag and writes no field on the contact, so the old `course-credentials-ready` and `course-access-granted` workflows can no longer be triggered and should be deleted in GoHighLevel. Any email a buyer gets after paying is one you built there yourself (e.g. on the *Payment Received* trigger).
7. **Password-reset email workflow** (the only email the app can cause, and only when the account's owner asks for it) -- trigger *Contact Tag Added*, tag `course-password-reset`, action *Send Email* merging {{contact.course_login_url}}: fired when a user submits `/forgot-password` (linked from the login page and the profile page). Without this workflow no email goes out at all, and a forgotten password has to be handled by hand. Here {{contact.course_login_url}} is a single-use `/reset-password` link that expires in 2 hours; the user chooses a new password there, keeps their username, and is signed in. A buyer who never finished setting up their login gets their `/activate` setup link through this same workflow, so word the email for both ("choose your password here"). Must end with *Remove Tag* `course-password-reset`, or a second request cannot fire it. The contact used is the one from the user's most recent purchase (accounts with no purchase need `GHL_LOCATION_ID` so the contact can be looked up by email). The form answers the same way whether or not the account exists, and sends at most one email per account every 2 minutes.
8. **Refund workflow** (optional but recommended) -- trigger on refund/chargeback for the product, action *Webhook*: `POST https://<your-domain>/api/webhooks/gohighlevel/refund` with the same `secret` and either `transaction_id` or the buyer's `email`. If that was the buyer's only un-refunded purchase, every paid course flips to REVOKED (content turns 403; free courses and the account survive). A later re-purchase re-activates them.

Every forgot-password handoff is recorded in the `EmailLog` collection (SENT = handed to GoHighLevel, FAILED = nothing went out). No password is ever generated, emailed, or stored in plaintext.

The webhook must reach the app over the public internet, so test against a deployed URL (or a tunnel to `localhost:3010`).

Paid courses can only be opened by a verified purchase: self-enrollment (the "Enroll" button, `POST /api/enrollments`) is refused for any course with a price unless the user manages it or is a buyer (holds at least one un-refunded GoHighLevel purchase).

### 5. Vercel Blob (needed on Vercel for uploading videos and files)

By default uploads are kept in a separate MongoDB database just for media (`parrot_media` on the same cluster as `DATABASE_URL`; override with `MEDIA_DATABASE_URL` / `MEDIA_DATABASE_NAME`). The browser sends each file in 3 MB parts, because a request body on Vercel is capped at 4.5 MB, and files are served back to signed-in users from `/api/media/file/...`. Files are limited to 100 MB this way. For larger course videos, connect Vercel Blob: in the Vercel dashboard, *Storage -> Create -> Blob*, create a **public** store and connect it to the project (this adds `BLOB_READ_WRITE_TOKEN`), then redeploy -- uploads then go straight from the browser to Blob.

Files in a public store are reachable by anyone who has the exact URL. The URLs carry a random suffix and are only handed to users with access to the lesson, but a buyer could copy one and share it -- the usual trade-off of direct video delivery.

## Free lessons page

`/free-courses` is a public page with no platform menu and no sign-in: it shows up to three videos from the free courses and ends with one button to the registration landing page (`REGISTRATION_URL` in `src/app/free-courses/page.tsx`). To fill it, create a course with price `0` in the admin panel, publish it, and add published *Video* lessons -- the first video of each free course is shown, then further videos in order until there are three. Only a published video of a published free course is ever listed, and only such a video can be streamed without an account (`/free-courses/video/{lessonId}`); videos of paid or draft courses stay behind the sign-in.

## Community and calendar

Both are stored in MongoDB (`src/features/community`, `src/features/calendar`).

- **Community** (`/community`, and the three buttons on the student dashboard): members post a question, a win, or a video for feedback. A video is uploaded to the platform's own storage (same uploader as course material, limited to video and 300 MB per file; 25 MB without Blob storage) -- a post can never embed an outside link. Members like, celebrate and comment; the author is notified of replies, and replies from an admin or instructor carry a "Coach" badge. A member can hide a post for themselves or report it; staff see the report count and, like the author, can delete the post (its comments and video go with it). Posting is rate-limited per member.
- **Calendar** (`/calendar`, and "Coming Up" on the dashboard): admins and instructors create events at `/admin/calendar` -- a live call or group session (members RSVP, and only then see the join link), a reminder, or a content release. Times are stored in UTC and shown in each viewer's own time zone; an all-day event is stored at 12:00 UTC of its date so it reads as the same day everywhere. "Add to Calendar" downloads an `.ics` file (`/api/calendar/events/{id}/ics`) or opens Google Calendar. An admin manages every event; an instructor the ones they created.

## Adding content in bulk

- **Drop files into a module** (`/admin/courses/{id}`, expand a module): drag in any number of videos or documents. Each becomes a lesson named after its file, in file-name order -- a video becomes a VIDEO lesson (its length is read automatically), anything else a DOCUMENT lesson linking to the file.
- **Import courses from a file** (`/admin/courses` -> *Import courses*): drop a `.csv` (opens in Excel; `,` or `;` separated) or `.json` file. CSV has one row per lesson with the columns `course_title, course_description, level, price, checkout_url, module_title, lesson_title, lesson_type, video_url, duration_seconds, lesson_description`; rows sharing a course and module name are grouped, and course-level columns only need filling on a course's first row. The dialog offers a template, previews what the file contains, and lists any problem by course/module/lesson name before anything is created. Imported courses arrive as drafts.

## Testing the purchase flow end-to-end

1. Simulate GoHighLevel's purchase webhook:
   ```bash
   curl -X POST https://<your-domain>/api/webhooks/gohighlevel/purchase      -H "Content-Type: application/json" -H "x-webhook-secret: $GHL_WEBHOOK_SECRET"      -d '{"email":"buyer@example.com","full_name":"Test Buyer","customData":{"transaction_id":"txn-test-1","payment_status":"succeeded"}}'
   ```
2. The app provisions the account (no password yet) and sends nothing to GoHighLevel -- no email results. The webhook response reports `newAccount` and `enrolledCourseSlugs`. Replaying the same `transaction_id` returns `duplicate: true` and provisions nothing new.
3. The buyer opens `/welcome` (where checkout redirects them), enters the checkout email, chooses a username and password and lands signed in on the dashboard. From then on they sign in at `/login` with that username (or the checkout email) and password — any other password is rejected — and have lifetime access to the purchased course. A repeat purchase by the same email keeps the existing credentials and just unlocks the new course.
4. Simulate a refund to revoke access (`duplicate`-safe as well):
   ```bash
   curl -X POST https://<your-domain>/api/webhooks/gohighlevel/refund      -H "Content-Type: application/json" -H "x-webhook-secret: $GHL_WEBHOOK_SECRET"      -d '{"customData":{"transaction_id":"txn-test-1"}}'
   ```
   The enrollment flips to REVOKED: the course disappears from the dashboard and its content returns 403, while the login itself keeps working.
